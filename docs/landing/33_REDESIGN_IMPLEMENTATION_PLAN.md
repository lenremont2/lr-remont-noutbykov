# План внедрения дизайн-системы «В вашем ритме»

29 октября 2026 · версия 1.0. Основа: [32_DESIGN_SYSTEM_V2.md](32_DESIGN_SYSTEM_V2.md).

Это исходный план внедрения, подготовленный до изменения production. Фактические результаты, делегирование, проверки и оставшиеся ограничения фиксируются в [34_DESIGN_SYSTEM_IMPLEMENTATION.md](34_DESIGN_SYSTEM_IMPLEMENTATION.md); действующая система — в документе 32. План сохраняет последовательность и критерии, не подменяет журнал завершения работ.

## 1. Результат и границы

Целевой результат: единая система жемчуг / графит / яркое золото на главной и детальных страницах, удобные реальные сценарии заявки, сохранённые содержание и SEO. Дизайн должен выдерживать длинную страницу и неодинаковый контент, а не только четыре демонстрационных секции.

| Входит                                                                  | Не входит автоматически                                           |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Токены, типографика, сетка, адаптивность, компоненты, формы и состояния | Новый бренд, другая гарнитура, смена Astro или frontend-фреймворк |
| Перенос выбранного формата и симптома в заявку                          | Новый backend, CRM, аналитика или личный кабинет                  |
| Главная, бренды, неисправности, отдельная MacBook                       | Новые SEO-страницы и изменение существующих URL                   |
| Реальные медиа, доступность, производительность, проверки               | Новая фотосессия как обязательное условие всей работы             |
| Локальная статическая сборка                                            | WordPress-экспорт, публикация, credentials, изменения плагинов    |

Новая съёмка может улучшить результат, но имеющихся материалов достаточно для первого внедрения. Недостающий факт не заменяется вымыслом. Содержательный конфликт фиксируется в соответствующем проектном документе, а не блокирует независимые визуальные работы.

## 3. Последовательность и зависимости

Путь внедрения: **базовая фиксация → токены и первый вертикальный сценарий → цена и условия → оставшаяся главная → шаблоны → общая проверка**.

В каждом этапе реализуется и проверяется законченный пользовательский сценарий. Не нужно сначала переделывать CSS всех страниц, а потом восстанавливать формы. Общие токены имеют широкий эффект: их изменение требует немедленного просмотра хотя бы одной страницы каждого семейства.

Этапы — порядок исполнения, не новые запросы разрешений. Отдельное решение пользователя требуется только при реальном изменении исходного объёма, фактов или утверждённой архитектуры.

## 4. Этап 0 — зафиксировать основу

**Задача:** получить сравнимую точку до изменений и не потерять накопленные материалы.

| Работа                                        | Артефакт / место                              | Критерий завершения                                                                               |
| --------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Проверить текущие инструкции, diff и сценарии | AGENTS, manifest/lockfile, существующие tests | Пользовательские изменения учтены; нет массового reset или format всего дерева                    |
| Составить список всех маршрутов из данных     | service-pages.json, service-pages.ts, pages   | Каждый маршрут отнесён к главной, бренду, проблеме, MacBook или preview                           |
| Зафиксировать внешний вид до миграции         | Существующая папка artifacts или .taste-skill | Desktop/mobile главной и по одному образцу каждого шаблона                                        |
| Зафиксировать состояние проверок              | npm run quality, node --test tests/*.test.mjs | Ошибки базы названы отдельно; старый сбой не выдаётся за результат нового изменения               |
| Сверить спорные факты                         | Документы 22/25/26/29 и источники данных      | Диагностика, гарантия, роль точек, отзывы и директор не получают новых неподтверждённых трактовок |

Не проводить повторный полный контент-проект: ранее принятые решения сохраняются. Неактивный RepairCases не возвращается без реального материала и отдельной задачи.

## 5. Этап 1 — основание системы и первая заявка

**Вертикальный сценарий:** человек понимает услугу → выбирает формат → открывает заявку → видит выбранный формат → может изменить → вводит телефон.

| ID    | Работа                                                 | Основные файлы                                 | Критерий приёмки                                                                 |
| ----- | ------------------------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------------------------- |
| DS-01 | Перенести базовые и смысловые цвета                    | styles/core/_variables.scss                    | Основная палитра совпадает с документом 32; нет подмены bright gold на champagne |
| DS-02 | Нормализовать контейнер, типографические роли, радиусы | Существующие core/layout SCSS и SectionHeading | 390/768/1440 читаемы; длинный текст не ломает сетку                              |
| DS-03 | Переоформить общие действия и поля                     | LeadButton, LeadForm, общие styles             | Видны hover/focus/pressed/error; новый цвет не скрыл границы полей               |
| DS-04 | Перенести композицию выбранного hero                   | sections/Hero.astro, его SCSS                  | Понятны услуга и город; один H1; выбор и действие доступны на mobile             |
| DS-05 | Связать формат с существующим контекстом               | scripts/landing.js, Hero, LeadForm             | mobile→mobile-lab, home→at-home, center→workshop, courier→courier                |
| DS-06 | Оформить dialog и контекст заявки                      | LeadModal, LeadCapture, LeadForm               | Escape, закрытие, возврат фокуса; выбранное видно; ввод не теряется              |

**Сценарии проверки:** каждый из четырёх форматов; консультация без выбора; смена формата после открытия; закрытие/повторное открытие; пустой/невалидный телефон; поля выезда; no-JS контакт; клавиатура и мобильная клавиатура.

**Проверка общей зоны влияния:** после токенов просмотреть главную, бренд, проблему и MacBook. Локальные старые синие HEX и тени не должны случайно оставаться внутри уже перенесённой композиции. Ещё не перенесённые секции явно считаются промежуточным состоянием, не завершённой системой.

**Не делать:** новый менеджер состояния, localStorage для телефона/адреса, URL с персональными данными, второй комплект форм, полную перепись landing.js.

## 6. Этап 2 — цена и информированный выбор

**Вертикальный сценарий:** выбрать проблему → понять ориентир и ограничения → посмотреть полный прайс → обратиться с сохранённым контекстом.

| ID    | Работа                                  | Основные файлы                          | Критерий приёмки                                                                              |
| ----- | --------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------- |
| DS-07 | Перенести белую панель выбора ориентира | HomePricing.astro, соответствующий SCSS | Три radio, реальная работа/цена/срок, стабильная высота и понятный выбор                      |
| DS-08 | Сохранить все условия production-цены   | HomePricing, laptop-service.json        | Детали отдельно, модель/диагностика, срочная диагностика, скидки и оплата частями не потеряны |
| DS-09 | Обновить полный прайс                   | ServicePriceTable, PriceVerification    | Строки и заголовки доступны, no-JS работает, дата сверки реальная                             |
| DS-10 | Передавать выбранную проблему           | landing.js, существующий контекст формы | Симптом не сбрасывает формат; данные объясняют запрос, не обещают диагноз                     |

Прайс не собирается парсингом видимой строки «от … ₽». Используется исходное поле данных. При перестановке строк массива нельзя молча связать выбор с другой работой: использовать имеющийся устойчивый ключ либо ввести локальное явное соответствие, покрытое небольшой проверкой.

**Проверки:** все варианты + полный прайс; только клавиатура; screen reader для связи выбора/результата; mobile 320/390; длинное название работы; смена выбора без скачка страницы; цена → форма → смена формата → сохранённый симптом.

**Обязательный просмотр:** вся главная последовательно на desktop и mobile, а не только отдельные компоненты. Проверить повторы CTA, длину страницы, чередование фонов, отступы между соседними блоками и нижнюю закреплённую панель.

Текущие наборы: design-concepts, hero-video, landing, phone, quiz, reviews, service-pages, visit. Для CSS-полировки не добавлять тесты, которые только повторяют значение радиуса. Для новой связи контекста нужен небольшой поведенческий регрессионный тест.

Сборка проверяет компиляцию и маршруты; она не проверяет отправку реальной заявки. Отправка на внешний обработчик без специальной договорённости не используется как тест. Если доступен только локальный интерфейс, отдельно фиксируется, что реальная доставка заявки не подтверждена.

## 12. Риски и способы удержать качество

| Риск                                                     | Почему существенен                                       | Действие                                                                  |
| -------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------- |
| Глобальная замена цветов ломает дочерние страницы        | Общие токены затрагивают много компонентов               | Ранний просмотр каждого семейства, отдельные контрастные роли             |
| Макет превращается в новый набор дублирующих компонентов | Легко перенести DesignService целиком рядом с production | Выделять только повторяемое, данные и формы сохранять существующие        |

## 13. Приоритеты и точки готовности

**P0 — единая основа и рабочее обращение:** DS-01–10. Без корректного выбора, цены и формы редизайн не считается жизнеспособным, даже если медиа выглядит завершённо.

**P1 — полноценная главная и семейства:** DS-11–26. Это основной объём внедрения, не факультативный список улучшений.

**P0 перед завершением — общая проверка:** DS-27–32. Проверки выполняются также по ходу этапов; финал подтверждает систему целиком.

**Позже, при отдельной необходимости:** новая предметная съёмка; локальные шрифты после измерения; расширение фотопросмотра; новые реальные кейсы. Эффекты и новые секции не добавляются, пока они не решают конкретную задачу.

Календарные сроки здесь не обещаются: сначала необходимо выполнить первый вертикальный сценарий и увидеть реальный объём исключений. Последовательность и критерии позволяют оценивать остаток по завершённым результатам, а не по проценту перекрашенных файлов.

## 14. Финальная приёмка

Система готова к передаче, когда одновременно выполнено следующее:

1. Главная, бренды, проблемы и MacBook используют выбранную визуальную основу; исключения объяснены.
2. Состав содержания, уникальность страниц, маршруты, canonical и JSON-LD сохранены.
3. Выбранные формат/симптом доходят до формы, видны человеку и могут быть изменены без потери ввода.
4. Цены и условия не превращены в неподтверждённые обещания; источники и даты сохранены.
5. Клавиатура, mobile, no-JS, reduced motion и ошибки проверены в относящихся сценариях.
6. Нет новых глобальных selectors, browser globals, лишних зависимостей и дублирующих форм.
7. npm run quality и нужные поведенческие тесты прошли; рендер и ограничения описаны отдельно.
8. Итоговый отчёт показывает реальные desktop/mobile состояния, перечисляет оставшиеся ограничения и не называет сборку полным аудитом или подтверждением доставки заявки.

Последовательность исходного плана начиналась с этапа 0 и законченного сценария этапа 1. Текущий результат, выполненные проверки и оставшиеся ограничения описаны в журнале 34. Публикация и WordPress остаются отдельной задачей.
